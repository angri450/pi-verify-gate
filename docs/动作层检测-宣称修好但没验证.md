# 动作层检测：宣称修好但没验证

动作层第一版跑完（277 个会话、1,719 个带收尾文本的轮次）。三个检测器里**一个有真效果**：模型宣称修好，而这一轮里工具报过错——这类轮次的文件**后续被返工率 36.2%**，是普通轮次的 1.8 倍（20.4%），Fisher 检验 p=0.0056。这是整条线索上第一个统计显著、且不依赖用户配合的信号。

## 验证标签换成"返工"

用户纠正这个标签在动作层同样失效（检测出的轮次纠正率 0.075~0.108，还低于基线 0.123——用户根本没看出来）。所以换成纯内部一致性的标签：

**返工 = 这个轮次改过的文件，在本会话后面又被改了一次。** 不需要用户说话，只看会话自己的行为。

## 结果

按会话切分，1,719 个带收尾文本的轮次，总返工率 21.2%：

| 组 | n | 之后被返工 |
|:--|--:|--:|
| **宣称修好 + 这轮有工具报错** | 105 | **36.2%** |
| **宣称修好 + 没跑测试** | 146 | **32.9%** |
| 宣称修好 + 没报错 | 67 | 16.4% |
| 宣称修好 + 跑过测试 | 26 | 3.8% |
| 不宣称（普通收尾） | 1,547 | 20.4% |

显著性：

- 宣称修好 + 没跑测试 vs 普通收尾：p = 0.0010
- 宣称修好 + 没跑测试 vs 宣称修好 + 跑过测试：p = 0.0016
- 同样宣称修好，有报错 vs 没报错：p = 0.0056

最有判别力的两个格子连起来就是硬撑的可操作定义：**嘴上说修好了，但这轮自己的命令报过错，或者根本没跑过任何测试。** 对照组显示"跑过测试再宣称"几乎不会返工（3.8%），说明返工不是宣称本身造成的，是缺验证造成的。

## 没用的两个检测器

**失败后重复同一命令**：有失败动作的轮次 761 个，之后重试那条失败命令的只有 1.3%。整库重复跑过且失败过的命令 33 条（重复 2 次 13 条、3 次 12 条，最多 9 次 1 条）。antiloop 那类循环检测在你的会话里能抓的东西极少，不是主力。

**宣称"测试通过"却没跑测试**：全库只有 6 例，模型基本不犯这种错，样本量不足以下结论。

## 插件怎么落地

检测规则（全部在 `message_end` 可拿到的数据里，不用新钩子）：

```
命中条件 = 收尾文本匹配宣称正则（已修复|搞定|修好了|fixed|resolved|工作正常|验证通过…）
         且（本轮没有任何测试命令 或 本轮有任一工具报错）
```

触发动作按强度分两级：

1. **提示级**（默认）：footer 或系统消息插一条"这轮宣称修好但没跑测试，建议先跑一遍"，不打断
2. **强制级**：`turn_end` 里 `continue: true` 追加一轮自查提示，让模型自己去跑测试再收工

数字依据：命中后有 36.2% 的概率这事真没做完（基线 20.4%）。精确率这个水平适合提示，不够自动拦截——拦截要等更强的信号。

## 已装成插件（2026-10-10）

规则落成个人扩展 `~/.pi/agent/extensions/verify-gate/index.ts`，每个会话自动加载，README 在 `~/.pi/agent/extensions/verify-gate/README.md`。

三个隔离测试（`pi -ne -e <路径> --print --mode json`，关掉其他扩展）：

| 用例 | 期望 | 实际 |
|:--|:--|:--|
| 收尾说"已修复，搞定了"，没跑测试 | 触发，reason=no-test | 触发 1 次，no-test |
| 收尾说"文件已经读完了"，无成功宣称 | 不触发 | 0 次 |
| 先跑 `npm test`（失败）再说"已修复" | 触发，reason=tool-error | 触发 1 次，tool-error（bash） |

实现要点：一轮 = 一次用户提问到下一条用户提问，`before_agent_start` 清账；`tool_call` 认测试命令、`tool_result` 记报错；`message_end` 只取没有 toolCall 的收尾消息；跑过测试且没报错放行，同一轮只报一次。插件自己插进去的提示会触发模型续跑，不计为新的一轮（否则会重复报）。

已知局限见扩展目录里的 README：精确率 29.3% 所以是提示不是拦截；测试命令只认正则，codemode 和 subagent 里的测试看不到。
